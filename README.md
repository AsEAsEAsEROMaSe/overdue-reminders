# Нагадування про прострочені задачі

Щоранку о 10:00 за Києвом кожен виконавець отримує в Telegram одне повідомлення зі своїми простроченими задачами.
Прострочена задача: дедлайн раніше за початок поточної доби за Києвом і статус не `done`.
Хто не має прострочених задач, повідомлення не отримує.

Тут лише логіка одного запуску і моки в пам'яті. Справжніх Telegram, бази і планувальника немає.

Де агент відступив від брифу і як це помічено: [REPORT.md](REPORT.md). Журнали роботи як доказ: [journal/](journal/README.md).

- `isReminderTime(now)`: чи зараз час нагадування. Її викликає планувальник.
- `runDailyReminders(now, deps)`: один запуск, повертає звіт `{ sent, skipped, failed }`.

## Як запустити

Потрібен Node 22.18 або новіший: vitest 5 вимагає 22.12+, а `npm run demo` запускає `.ts` напряму, що Node уміє без прапорців з 22.18.

```bash
npm install --no-bin-links
npm test                # vitest run
npm run typecheck       # tsc --noEmit
npm run check:headers   # звірка JSDoc-шапок з import
npm run check:mutations # 53 навмисні помилки в коді, кожну мають зловити щонайменше 2 тести
npm run coverage        # які рядки й гілки src/ виконують тести
npm run demo            # імітація дня в консолі з кольорами (без кольорів: NO_COLOR=1 npm run demo)
```

На диску проєкту не працюють символьні посилання. Через це `npm install` без `--no-bin-links` падає з EPERM, а `npx vitest` і `npx tsc` не знаходять бінарників.
Скрипти в `package.json` викликають ті самі інструменти напряму через `node node_modules/...`.
На звичайному диску працюють і `npx vitest run`, і `npx tsc --noEmit`.

## Як влаштовані тести

- Кожен тест перевіряє одну поведінку і має три частини: підготовка, дія, перевірка (Arrange, Act, Assert).
- Дані будуються через `test/builders.ts`; касти для «старих» записів лише там.
- Усе тестове створюється наново в кожному тесті: моки (`makeDeps`, `buildDeps`), задачі (`threeOverdueTasks()`), користувачі (`threeUsers()`), дати (`nowAt10()`, `laterSameDay()`, `nextDay()`) і порожній звіт (`emptyReport()`). Спільні між тестами лише рядки й числа (`DAY`, `SEND_TIMEOUT_MS`), які неможливо змінити. Випадкових даних немає: кожен запуск тестів дає той самий результат.
- Залежності задаються один раз при створенні (`makeDeps`, `buildDeps`, `depsWithTimeout`, `depsWithAttemptLog`, `depsWithLock`) і потім не міняються; збійні сховища й месенджери лежать окремими класами в `test/faulty.ts`.
- Окремі тести перевіряють, що запуск не змінює вхідні задачі й користувачів (`Object.freeze`).
- На кожну змінну, параметр, поле і гілку є тест, де її зміна міняє результат. Кожну з 53 мутацій ловлять щонайменше два тести: скрипт це перевіряє і падає, якщо якусь ловить лише один.
- Покриття: 99.5% рядків, 97.7% гілок. Не покрито два рядки, до яких не дійти: гілка `hang` у моку після вичерпних перевірок і `throw` у `startOfKyivDay` (захист на випадок зміни правил часу).
- Перевіряються реальні значення строгою рівністю: кому і який текст пішов, повний звіт.
- Таймаут перевіряється на підробленому годиннику vitest, без справжнього очікування.
- Час завжди прибитий: `now` передається параметром.
- `npm run check:mutations` по черзі ламає код у 53 місцях і перевіряє, що тести це помічають. Тести, що не завантажились (наприклад, синтаксична помилка), рахуються як упалі. Ctrl+C посеред прогону повертає змінений файл.

## Як працює запуск

1. `Lock.acquire('daily-reminders:' + день)`. Зайнято: повертає порожній звіт. `release` у `finally`; його збій не губить звіт (припущення 22).
2. Бере невиконані задачі і вибирає прострочені. Задачі без дедлайну чи виконавця йдуть у `skipped`.
3. Для кожного виконавця:
   - немає в `UserRepo` або немає `telegramChatId`: `skipped`;
   - `SentLog.has(userId, день)`: вже отримав, пропускаємо;
   - сьогодні вже вирішено не пробувати (`AttemptLog.getStopReason` не `undefined`): `failed` з тією ж причиною (`blocked` або `attempts_exhausted`), без відправки;
   - інакше спроба: лічильник плюс один, відправка з таймаутом.
4. Успіх: `SentLog.mark` і `sent`. Збій: `failed` з причиною, `mark` не ставиться, решта отримують своє.

У коді це дві функції. `runDailyReminders` бере блокування і йде циклом по виконавцях. `remindUser` обробляє одного виконавця і повертає результат (`sent`, `already_sent`, `skipped` або `failed`), а цикл записує його у звіт.
Таймаут: `sendWithTimeout` ставить таймер; хто перший, відповідь Telegram чи таймер, той і вирішує результат, а відповідь прибирає таймер.

Причини у `failed`:

| reason | коли | final |
|---|---|---|
| `rate_limited` | Telegram 429 | `true` лише на третій спробі |
| `timeout` | відповіді немає за `sendTimeoutMs` | `true` лише на третій спробі |
| `error` | інша помилка | `true` лише на третій спробі |
| `blocked` | Telegram 403, і кожен наступний запуск того дня | завжди `true`, більше того дня не пробуємо |
| `mark_failed` | повідомлення доставлено, але `SentLog.mark` упав: наступний запуск надішле вдруге | `false` |
| `attempts_exhausted` | наступні запуски дня після третьої невдалої спроби | завжди `true` |

## Припущення

1. **Лічильник спроб.** Бриф вимагає не більше трьох спроб на день, але порту для цього не дає. Додано порт `AttemptLog`: `count` і `add` для спроб, `stop(userId, day, reason)` і `getStopReason` для «сьогодні більше не пробувати» разом із причиною, щоб звіт і в пізніших запусках казав `blocked`, а не `attempts_exhausted`.
2. **403.** Користувач іде у `failed` з `blocked` і `final: true`, викликається `AttemptLog.stop` з причиною `blocked`; наступні запуски того дня теж пишуть `blocked`. «Повідомити» означає запис у звіті; окремого каналу для адміна немає.
3. **Таймаут.** `deps.sendTimeoutMs` обов'язковий, щоб не було прихованого значення за замовчуванням (для Telegram розумно 10000). Таймаут рахується як спроба і повторюється наступним запуском, як 429.
4. **Паралельний запуск.** «Кожен отримує рівно одне повідомлення» означає одне на кожного користувача. Другий запуск при зайнятому блокуванні повертає порожній звіт.
5. **Звіт** містить лише id користувачів і задач та причини. Chat_id і тексту повідомлень у звіті немає, логів код не пише.
6. **Невалідна дата дедлайну** обробляється так само, як відсутня: `skipped` з `no_deadline`.
7. **`isReminderTime(now)`** істинна всю годину 10:00…10:59 за Києвом. `runDailyReminders` її сам не викликає: вирішує планувальник.
8. **Хто вже отримав** повідомлення сьогодні і хто не має прострочених задач, у звіт не потрапляє.
9. **Шапка `src/run.ts`.** Бриф каже, що в головного файлу лише список нижчих. Але `run.ts` імпортує тест, а правило повних списків вимагає вписати його в «Головний». Тому там один рядок: `test/run.test.ts`.
10. **Текст повідомлення:** `Прострочені задачі: N`, далі нумерований список `назва (дедлайн ДД.ММ.РРРР ГГ:ХХ)` від найстарішого дедлайну. Години 00…23 (`hourCycle: 'h23'`).
11. **Порти асинхронні** (повертають Promise), бо справжні база і Telegram асинхронні.
12. **Збій сховища для одного користувача** (UserRepo, SentLog.has, AttemptLog) записується у `failed` з `error`, решта отримують. Якщо впав саме `SentLog.mark` після успішної відправки, причина окрема, `mark_failed`: повідомлення вже доставлено, і наступний запуск надішле його вдруге. Краще дубль, ніж пропущене нагадування; тест це фіксує.
13. **Відповідь, що прийшла після таймауту**, вже не враховується: спроба записана як `timeout`, і наступний запуск може надіслати повторно.
14. **Незмінність даних.** Поля `Task`, `User`, пропущених і невдалих записів та `RunDeps` позначені `readonly`, вхідні масиви приймаються як `readonly Task[]`: спробу змінити їх ловить tsc. Звіт і масив задач у групі звичайні, бо код заповнює їх по ходу.
15. **Дедлайн рядком** (а не `Date`) і `null` вважаються відсутнім дедлайном: `no_deadline`. Сховище має віддавати `Date`.
16. **Порядок перевірок задачі:** спершу `done`, потім дедлайн, потім виконавець, потім чи прострочена. Тому задача без дедлайну і без виконавця дає одну причину `no_deadline`, а задача без виконавця з майбутнім дедлайном теж іде у `skipped`: погані дані звітуємо завжди.
17. **Збій `AttemptLog.stop` після 403** записується як `error` з `final: false`, і наступний запуск спробує знову. Без працюючого журналу спроб інакше не запам'ятати.
18. **Невалідний `now`** кидає RangeError до взяття блокування.
19. **Відповідь Telegram рівно на межі таймауту** вважається таймаутом: таймер ставиться раніше за відправку.
20. **Довжина повідомлення не обмежена.** Telegram приймає до 4096 символів; у людини з дуже великою кількістю прострочених задач відправка впаде з помилкою. Бриф цього не вимагає.
21. **Блокування без строку дії.** Порт `Lock` з брифу не має TTL: якщо процес упаде між `acquire` і `release`, справжня реалізація має знімати блокування сама (наприклад, за часом). Це на боці реалізації порту.
22. **Збій зняття блокування.** Якщо `Lock.release` кидає помилку, запуск її ковтає: звіт повертається як є, а помилка бази чи іншого кроку, що сталася раніше, не підміняється помилкою блокування. Ключ блокування містить день, тож наступного дня він інший; у межах дня блокування має зняти TTL справжньої реалізації (припущення 21).
